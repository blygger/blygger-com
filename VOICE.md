# Voice

How the Blygger sites and docs speak. One guide, kept as **identical copies** in
[`blygger-org`](https://github.com/blygger/blygger-org/blob/main/VOICE.md) and
[`blygger-com`](https://github.com/blygger/blygger-com/blob/main/VOICE.md) —
change both, in the same sitting.

Written 2026-10-06 after a pass that found blygger.org speaking as "we" (the
protocol's first author and an AI assistant) about everyone else as "strangers"
and "other people's". Most of the clients, and much of the reference client, are
now built by people that voice placed outside. It misdescribed the project, and it
read as a gate.

## The rule

**Speak for the ecosystem and everyone building it. Nobody is an outsider.**

The subject of a sentence is the protocol, the project, a named piece of software,
or a named person — not an implied "we" set against everyone else.

## In practice

| Instead of | Write |
|---|---|
| we, us, our (the project) | the protocol, the project, the spec, the directory |
| our client, ours | Blygger Studio, the reference client |
| other people's clients, not ours | independent clients, other implementations |
| strangers | newcomers; readers who don't know you yet |
| from the outside, outside contributor | name the contribution, or say *independent* |
| tell us | open an issue, add it to the index, say so |
| our mistake | Blygger Studio's mistake (the software's, by name) |
| passes our tests | passes the reference client's tests |
| anyone but its authors | anyone, from the spec alone |

- **Address the reader as *you*.** That is inclusive. The trouble is never
  *you*; it is a *we* that the reader is not part of.
- **Name people for what they did.** Credit by name and link the work. Use a
  person's name, or *they*, unless their pronouns are stated; never infer
  pronouns from a name.
- **"Core contributor" is a label, not a border.** It marks sustained work on the
  protocol and the reference client. Nothing else on the page should imply that
  anyone without it is outside the project.
- **Own mistakes through the software, plainly.** "Blygger Studio shipped a
  generic default title" is clearer than "our mistake", and it tells the reader
  which code to look at.
- **State facts about other people's sites; don't editorialise.** The directory
  shows what a re-check found ("unreachable", "plain HTTP"), not a judgement of
  the site or its author.
- **Prefer a link to a count that goes stale.** "The ecosystem index lists every
  known client" stays true; "seven clients, six not ours" was wrong within a week.

## Where it applies

Every hand-written page on blygger.org and blygger.com, form text and messages the
sites send back, READMEs, technical notes, and issue or PR replies written in the
project's name.

**Not** to normative spec text, where *we* and *us* name the publishing blyg ("the
last version we saw", "does not reference us"). That is protocol-writing convention,
not a speaker.
